# 필름장이 통합 비서 설계 및 구현 상태

2026-11-02 · Android companion branch

## 목표와 기본 흐름
앱 시작 화면은 대화다. 메뉴에는 대화 목록, 전체 기능, 설정을 둔다.
질문 → 의도·기간·대상 파악 → 권한 확인 → 조회 또는 변경안 제시 → 사용자 확인 → 기존 업무 API 실행 → 실제 결과 안내 순서로 연결한다.

현재 구현은 제한된 로컬 문장 해석기이며 범용 대화 모델이 아니다. 모르는 명령은 지원되는 표현을 안내한다. 사용자 발화를 임의 SQL, URL, API 이름으로 실행하지 않는다.

## 이번 구현
- 한국시간 기준 오늘·내일·모레·어제·이번 주·다음 주·지난 주·주말·이번 달·다음 달·명시 날짜 조회.
- 관리자: get_my_company 기반 활성 업체 확인 후 사용자 토큰과 기존 RLS를 통해 해당 업체 sites 조회.
- 시공자: 기존 my-sites API가 허용하는 배정 현장만 사용하며 선택 업체로 필터링.
- 현장명·주소·고객명·전화번호 텍스트 검색. 결과는 최대 20개 표시하며 생략 사실을 안내.
- 결과 번호로 현장 상세 조회. 이전 결과는 업체 ID와 함께 저장하고, 상세 조회 시 권한과 현장을 다시 조회.
- 견적·재고·입금·수익·시공자·거래처·고객채팅·고객페이지·사진견적·시공실적·완료보고·재단·출퇴근·샘플·구인구직을 기존 업무 화면으로 연결.
- 업무 화면 연결은 완료로 표시하지 않으며 웹앱 계정 확인 후 연다. 웹과 Android 세션 자동 공유는 아직 구현하지 않았다.
- 기존 상담 등록의 요청 ID 재사용과 기존 현장 추가 확인 흐름 유지.

## 확장 구조
AssistantRequests는 의도와 타입이 지정된 인자를 반환한다. AccountAuth는 현재 사용자와 업체 권한을 확인하여 데이터를 읽는다. 화면은 결과를 대화로 표현하고 허용된 기능 목록만 연다.
향후 모델 해석기를 추가해도 실행 계층은 동일한 허용 목록과 인자 검사를 사용한다. 모델은 SQL·인증정보·서버 키를 생성하거나 보관하지 않는다.

변경 명령에는 pending_action { request_id, user_id, company_id, action, target_id, expected_version, arguments, expires_at }를 저장한다. 모호한 대상은 선택을 받고, 확인 후에도 현재 권한과 데이터 버전을 재검사한다. 네트워크 오류는 ‘실패’와 ‘결과 미확인’을 구분한다. 요청 ID와 결과를 서버에 기록해 재시도 시 중복 쓰기를 방지한다.

## 다음 구현 순서
1. 기존 일정 변경·배정 API의 조건과 알림 부작용을 조사하고 변경 전/후 미리보기 및 확인 흐름 연결.
2. 견적 초안·자재 재고·미수 조회를 대화 결과 카드로 연결.
3. 반출·반입·입금·보고서 쓰기에 요청 ID와 충돌 확인 적용.
4. 사진 첨부·음성 메시지·자연어 모델 해석기와 현장 문맥 연결.

## 검증과 범위
문장 해석, 날짜 경계, 변경 명령 구분, 기능 권한을 단위 테스트한다. Android 전체 빌드와 기존 테스트를 실행한다. 실제 기기의 로그인 세션으로 서버 전체 흐름을 검증하기 전에는 현장 조회 성공이나 실제 등록 완료를 주장하지 않는다. 이번 작업에서는 고객 현장을 생성·수정하거나 메시지를 발송하지 않는다.
