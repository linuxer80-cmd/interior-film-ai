# 현장 제안 → 시공자 지원 → 관리자 선택 → 배정

일반 구인 공고는 여러 시공자가 지원하고, 업체가 지원자 목록에서 상세정보를 본 뒤 필요한 사람을 최종 확정한다. 업체가 확정한 시공자에게만 배정 알림과 내 현장이 생긴다.

개별 현장 제안도 같은 확정 원칙이다. 여러 업체가 제안하면 시공자는 조건을 비교하고 원하는 현장에 지원한다. 지원 시 프로필·연락처 공유에 동의하지만 현장 배정이나 구직 날짜 삭제는 발생하지 않는다. 업체 관리자는 제안에 응한 지원자도 목록과 상세정보에서 확인하고 선택한다. 최종 배정은 기존 일당·권한·일정 충돌 검증과 일당 스냅샷 저장을 거친다.

최종 배정된 날짜만 구직에서 제외하며 남은 날짜는 유지한다. 같은 날짜에 겹치는 해당 시공자의 다른 지원·제안은 만료한다. 다른 지원자와 일반 구인 공고 자체는 유지한다. 날짜 일부가 겹치는 다일 공고는 전체 날짜 참여가 불가능하므로 해당 지원이 만료된다. 배정 취소 시 구직을 임의로 다시 공개하지 않는다.

## 적용 순서
1. 최초 설정은 `database/labor_job_proposals.sql`을 실행한다(이미 실행했다면 생략).
2. 이번 앱 변경 배포 후 `database/labor_proposal_applications.sql` 전체를 앱 운영 DB의 SQL Editor에서 실행한다. `settings={"version":2}`를 확인한다.
3. 앱을 새로고침한다. 업데이트 SQL 전 신규 제안 지원·확정은 비활성화되며 일반 공고 흐름은 유지된다. API도 버전 1의 즉시 배정 함수를 지원 처리로 오용하지 않도록 차단한다.
4. 테스트 계정으로 여러 제안→지원→관리자 목록·상세정보→한 현장 최종 확정→내 현장 및 남은 날짜를 확인한다.

과거에 확정된 배정은 변경하지 않는다. 기존 제안 대기 기록은 새 지원 방식으로 처리하며, 적용 전 이미 확정된 기록은 유지한다. 기존 기본 SQL을 업데이트 SQL 뒤에 다시 실행하면 이전 응답 함수로 돌아가므로, 새 설치에서는 반드시 위 순서로 실행한다.

## 검증
로컬 PGlite에서 실제 기존 SQL과 추가 SQL을 함께 실행했다. 여러 업체의 제안에 지원만 한 경우 배정 0건·날짜 유지, 관리자 확정 시 배정·일당 스냅샷·겹치는 지원 만료를 확인했다. 다른 업체의 확정 차단, 일당 변경 시 미확정 유지, 일반 공고 다수 지원자 중 선택, 재실행 및 RPC 실행 권한도 확인했다.

관련 DB·UI·상세정보 테스트 12개, API 테스트 5개 통과. 앱 빌드 성공. 운영 DB 적용과 로그인 계정 종단간 검증은 별도이며 현재 연결된 Supabase 프로젝트에는 앱 테이블이 없어 직접 적용하지 않았다.
