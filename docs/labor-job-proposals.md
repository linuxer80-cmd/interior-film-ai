# 현장 제안 → 수락 → 배정

관리자는 업체 연결 후 일당을 확인할 수 있는 구직자에게 현장 날짜를 제안한다. 생성 시 기존 배정이나 구직 날짜를 변경하지 않는다. 제안은 해당 업체와 수신 시공자에게만 표시한다.

시공자가 제안 날짜·일당·연락처 공유에 동의하고 수락하면 기존 labor_action_registered_wage의 권한·일당·일정 충돌·배정 스냅샷 검증을 거쳐 배정한다. 전 과정은 한 트랜잭션이다. 일당 또는 현장 날짜가 바뀌면 제안을 다시 확인해야 하며 중간 지원 상태나 연락처 공유가 남지 않는다. 거절은 구직 날짜를 보존한다. 수락·거절 재요청은 중복 배정을 만들지 않는다.

일반 지원자 확정에도 확정된 날짜만 구직에서 제외한다. 남은 미래 날짜와 기존 공개 의사를 유지하며, 남은 날짜가 없으면 구직을 종료한다. 배정 취소 시 날짜를 자동으로 다시 공개하지 않는다.

관리자 모집 현황은 현장별로 접고, 펼치면 날짜별 확정 인원과 공고·개별 제안별 모집 인원을 표시한다. 일반 공고 지원·관리자 확정 흐름은 유지한다. 과거 invited 기록은 기존 지원 흐름으로 확인 가능하다. 신규 개별 제안은 즉시 배정하지 않는다.

## 적용
1. 앱 변경 배포 완료를 확인한다. SQL 적용 전 신규 제안은 비활성화되며 일반 공고는 유지된다.
2. 실제 앱 DB의 SQL Editor에서 `database/labor_job_proposals.sql` 전체를 실행한다. 기존 labor_market_workflow, labor_market_consistency, worker_relationships 설정이 필요하다. 함수 버전이 예상과 다르면 트랜잭션 전체가 롤백된다.
3. 관리자·시공자 화면을 새로고침한다.
4. 읽기 전용 확인: `select public.labor_proposal_capabilities();` 결과 `{"version":1}` 확인.
5. 테스트 계정으로 제안→수락 또는 거절→날짜 유지 및 실제 현장 배정을 확인한다.

현재 연결된 Supabase 프로젝트에는 앱의 labor_jobs/labor_action이 없어 운영 DB 적용은 수행하지 않았다. 로컬 PGlite에서 실제 기존 SQL과 신규 SQL을 함께 적용해 검증했다.

검증: 신규 DB 5개·UI 3개·API 3개 통과. 앱 빌드 성공. 변경 후 전체 731개 중 통과 686·기존 실패 14·건너뜀 31(이후 일정 충돌 DB 테스트 1개 추가 통과). 운영 계정 종단간 검증은 DB 적용 후 필요하다.
